## "고칠 만한 차이"의 기준
- 오프닝: 같은 영웅 특성의 레이드 로그 오프닝 중 **과반(대략 60% 이상)** 이 가이드와 다른 순서를 보이면 고친다. 한두 개 로그만 다르면 고치지 말고 필요하면 note·caption에 "로그마다 다름"을 짧게 적는다. 풀 5초보다 먼저 쓴 사전 준비(징표·버프 등)는 로그에 안 보이니 "없음"을 근거로 지우지 않는다.
- 반복(단일): 로그 '다음에 누른 스킬' 표·예시 구간·APL 우선순위로 판단. 가이드가 A→B라 했는데 로그가 꾸준히 B→A면 고친다. 분당 1회 이상 누르는 핵심 버튼이 가이드 반복 흐름·영웅 탭 단일 우선순위에 아예 없으면 넣는다(APL 조건 확인). 가이드에 있는데 로그에서 거의 안 누르는 버튼은 다른 시전 번호로 찍히는지(대조 자료 맨 위 '시전 번호 → KB 스킬' 목록, 영어 이름*) 확인한 뒤 판단한다.
- 레이드는 독사의 심연 신화 님리사(쫄이 나오는 네임드)라 레이드 반복에도 광역기가 섞인다. 단일 순수 우선순위 판단에는 APL을 함께 본다.
- 광역: 쐐기 광역 풀 시작 순서·분당 시전(레이드 대비 배율)·APL aoe/cleave 목록으로 판단.
- 로그가 없는 영웅 특성(대조 자료에 '로그 없음')은 APL·공개 자료로만 보고, 근거 없이 바꾸지 않는다.
- 확실하지 않으면 바꾸지 말고 보고서에 "보류"로 적는다. 억지로 고칠 거리를 만들지 않는다. 맞는 가이드는 "변경 없음"이 정답이다.

## 고치는 곳 (모두 같은 순서를 말해야 한다)
`views/<ID>.json` 으로 본다.
- 개념서 2부 연습 장 타임라인: 단일(반복 흐름 rail + 영웅 특성별 끼워 넣기 rail), 오프닝(영웅 특성별 rail), 광역.
- 영웅 특성 탭 `heroBranches[i].opener.steps / singleTarget.priority / aoe.priority` (각 행: skillId, label, note, phase, trigger 등 기존 필드 유지).
- 같은 장의 본문·요점·실수·확인 문제·한 줄 원리(concept)·rail note가 순서를 말하면 함께 고친다. 3부 실전 영웅 특성 장에 순서 서술이 있으면 그것도 맞춘다. **고친 순서와 어긋나는 문장을 남기지 않는다.**
- 상단 `opener`·`priority`(화면에 안 나오는 예전 필드)는 건드리지 않는다.
- 특성 견본·기본 영웅 탭·목차·장 제목 구조·현장 팁(작성자 인용)·출처 목록은 이번 범위가 아니다(현장 팁 인용이 바꾼 순서와 정면으로 어긋나면 보고서에만 적는다).

## 탱커 6개 추가 작업 (warrior-protection, paladin-protection, deathknight-blood, demonhunter-vengeance, druid-guardian, monk-brewmaster)
화면은 이미 준비됐다. 데이터만 넣는다. 검사기(`validateTankCycles`)가 아래를 강제한다.
1. 영웅 탭 딜사이클 이름: `singleTarget.tabLabel = '레이드 단일'`, `aoe.tabLabel = '쐐기 광역'` (오프닝은 그대로). 제목에도 레이드/쐐기가 드러나게 다듬어도 된다.
2. 영웅 탭 탱사이클 두 개를 각 영웅 특성마다 새로 만든다(영웅마다 다른 부분은 다르게 — 같은 목록 복사 금지):
   - `tankRaid: { title(‘레이드’ 포함), summary(30자 이상), tabLabel: '레이드', talentBuildId: 'raid', steps: [...] }`
   - `tankMythic: { title(‘쐐기’ 포함), summary, tabLabel: '쐐기', talentBuildId: 'mythic-plus', steps: [...] }`
   - steps 행 형식은 opener.steps와 같다: `{ skillId, label, note(15자 이상), phase, trigger }`. 4~10행. 레이드는 탱 교대(도발 → 넘겨받는 순간의 방어 유지 → 탱 버스터 앞 생존기 순번 → 넘겨준 뒤 회복/자원 정리), 쐐기는 풀 단위(진입 → 방어 유지 켜기 → 큰 풀 생존기 순번 → 다음 풀 전 정리, 마법 피해 대응). 대조 자료의 '탱커 — 방어 기술 사용'(레이드 도발 간격·생존기 시각, 쐐기 풀 첫 90초)과 KB 스킬 설명·기존 3부 '방어 유지와 생존기 계획'·'쐐기 한 판'·'공격대 네임드' 장 본문을 근거로 한다. 숫자(분당 횟수·초)는 로그에서 확인한 범위로만 쓰고 단정하지 않는다.
   - 레이드 견본과 쐐기 견본의 특성이 다르면(예: 쐐기 견본에만 있는 생존기·차단) 그 차이를 summary나 note에 적는다. 견본 코드는 `views`의 talentBuilds와 `npm run kb:brief -- <ID>` 로 확인.
3. 개념서 3부 실전 장에 탱사이클 타임라인을 넣는다: '쐐기 한 판' 장과 '공격대 네임드' 장의 `timeline`에 `{ kind: 'tank', title: '쐐기 탱사이클 — …' / '레이드 탱사이클 — …', intro, rails: [...] }`. 이미 timeline이 없으므로 그 장에 새로 둔다(배열로 여러 개 둘 수도 있음). '방어 유지와 생존기 계획' 장에는 공통 방어 유지 반복 흐름을 `kind: 'tank'` 타임라인으로 넣어도 된다. rail 형식은 기존 타임라인과 같다(nodes: skillId·caption·above{skillId,when}, loop, note, kind:'inserts').
4. 2부 연습의 단일/광역 타임라인 제목은 탱커라면 "레이드 네임드(단일)"·"쐐기 풀(광역)"이 드러나게 다듬는다.
5. 도발: 전사 도발 355, 성기사 집행의 손길 62124, 수도사 조롱 115546은 KB에 있었고, 어둠의 명령 56222·고문 185245·포효 6795는 오늘 KB에 추가했다.

## 규칙 (어기면 안 됨)
- skillId는 `src/data/kb-skills.json`에 있는 것만. 찾기: `npm run kb:brief -- <ID> --find <낱말>` / `--id <번호>`. KB에 없는 스킬이 꼭 필요하면 **직접 KB 노트를 만들지 말고** 보고서의 "KB 추가 필요"에 적는다(이름·번호·이유). 임의 번역 금지.
- 스킬 설명(툴팁)은 고치지 않는다. 원고 문장에서 스킬을 부를 때는 KB의 한국어 이름 그대로 쓴다(그래야 아이콘·툴팁이 붙는다).
- 용어 고정: 네임드(보스·우두머리 금지), 쫄(졸개 금지, 조사 쫄이·쫄을·쫄은·쫄과), 딜사이클(로테이션 금지), 오프닝(오프너 금지), 쐐기(신화+ 금지), 극딜·발동·유지율. 근거 없는 사용률·인기 주장 금지. '12.1' 라벨 일괄 치환 금지.
- caption은 기존처럼 짧게(대략 14자 이내, 휴대폰에서 두 줄 넘지 않게). above.when도 짧게.
- 문장은 지금 원고의 말투(쉬운 존댓말, 짧은 문장)를 따른다. 번역투 금지.
- 다른 가이드·공용 파일(GuideDetailPage.js, 검사기, guideManuscripts.js 등)은 건드리지 않는다.

## 수정하는 방법 (직접 원고 파일·KB json을 손으로 고치지 않는다)
1. `patches/<ID>.cjs` 를 쓴다:
```js
// <ID> 딜사이클 순서 수정 — 근거: digests/<ID>.md, apl/<file>.simc
module.exports = {
  evidenceNote: '딜사이클 순서 대조(2026-10-20): 12.1.5 이후 WCL 상위 레이드 N개·쐐기 N개의 실제 시전 순서와 심크 APL(midnight d91a5707)을 대조해 …을 고쳤습니다.',
  changelog: `- 무엇을 → 어떻게 (근거: 로그 n/m개, APL 줄)\n- …`,
  apply(m) {
    const block = m.blocks.find(b => b.title.startsWith('…'));   // 장은 번호 말고 제목으로 찾는다
    block.timeline.rails[0].nodes = [ … ];                         // 새 값을 통째로 넣는다(push 금지 — 여러 번 돌려도 같은 결과)
    const hero = m.heroBranches.find(h => h.label === '…');
    hero.opener.steps = [ … ];
    return m;
  },
};
```
   바꿀 것이 없으면 `apply(m) { return m; }` 에 evidenceNote 를 "…대조했고 순서를 바꾸지 않았습니다(근거 요약)." 로 남긴다(changelog 는 같은 취지로 한두 줄).
2. 반영: `node apply-patch.cjs <ID>` (이 폴더에서). 항상 처음 정본에 적용하므로 고쳐서 다시 돌려도 된다. KB 정본·사이트 원고·KB patch-changelog.md 가 함께 바뀌고, 바뀐 순서가 `patches/<ID>.diff.md` 에 남는다. KB에 없는 skillId 가 있으면 중단된다.
3. 검사(사이트 폴더 `C:/wowmeta/site` 에서): `node scripts/validate-guide-manuscripts.js`, `node scripts/validate-guide-copy.js`, `node scripts/validate-guide-tooltips.js`. **다른 작업자가 동시에 다른 가이드를 고치고 있으니, 자기 가이드 ID가 들어간 오류만 고친다.** 탱커는 `tankCycles` 오류가 0이 될 때까지. `npm run sync-kb`·`npm run validate`·빌드·git 은 돌리지 않는다(마지막에 한 번 모아서 돌린다).
4. `patches/<ID>.diff.md` 를 다시 읽고 앞뒤 문장이 맞는지 확인한다.
